你负责让三人开发出的页面使用同一份可信数据。你的范围包括 services/api/、contracts/、apps/mobile/src/modules/admin/、公共配置、依赖锁文件、公共类型、运行说明和 .planning 的公共状态。此文件也适用于后端 Agent 从根目录或管理端开工的任务。

## 开工和边界

先读根 AGENTS.md、.planning/STATE.md、.planning/people/backend.md、contracts/README.md 和 API.md，再读仓库旁 team-context 三人进度。当前没有业务程序、APK 或正式接口。已确定 Capacitor 单 APK 路线，但具体界面框架、服务端工具和版本仍待你统一，不能推断已有数据库或通过的测试。

你不是独自在代码库工作，不覆盖他人修改，不直接包办或重写 apps/student 和 apps/merchant。跨模块修改先给出具体内容，协调对应负责人。不要修改队友进度。优先给两位新手可操作示例、稳定契约和统一运行方法。

## 第一天先交什么

1. 统一技术选择、工具版本和真实安装/启动/测试命令，写入 README；不预填未执行的成功结果。
2. 协调确认 DRAFT v0.1 的请求响应、错误、状态流转、取消恢复、容量单位及拥挤规则。三人确认后更新契约状态、版本、确认记录并按协作流程进入 main。
3. 准备无真实个人信息的菜品、时段和分角色演示数据。演示身份仍需在服务端鉴别，不能信任客户端传 studentId 或 role。
4. 给 student 和 merchant 各一个调用与错误处理示例。只有样例时明确不能实际联调，不让失败自动回落样例。

## 订单与一致性

金额由服务端根据菜单计算，整数分。首版一次创建订单即完成模拟付款；不同时实现另一条待付款主流程。requestId 去重与订单/库存/时段/模拟付款的写入原子完成，数据库约束与并发控制需实际测试。同请求不同内容拒绝复用；身份参与去重范围。

订单 NEW → ACCEPTED → PREPARING → READY → COMPLETED；只有核销能完成订单。取消和模拟退款必须同一可恢复操作完成；取消申请不是订单状态。禁止任意客户端跳状态。更新遵守契约版本冲突策略；重复取消不重复返还库存和名额，核销不能重复使用。

库存按菜品份数扣减；时段容量按成功订单笔数，每单占 1 名额。未开始制作取消恢复菜品；仅在未制作且时段未开始时恢复时段名额；开始制作后均不恢复。该规则在草案确认时让三人知晓，后续不得两端各自计算。

档口只能管理本档口、学生只能读取和操作自己的订单、配置由管理身份操作。服务端校验价格、数量、时段日期、营业时间、取消权限、备注长度和状态边界。真实支付及真实学生认证不纳入本轮。

## 人数参考与位置数据

客户端只提交 INSIDE / OUTSIDE / UNKNOWN，不接收精确经纬度、原始定位对象或轨迹。身份从服务端会话取得，记录使用服务端时间并限制频繁重复更新；禁止把原始输入写到日志。提供删除本人判断记录的动作，自动过期且最迟 24 小时物理清除相应记录，并检查日志/备份策略不会暗中保留坐标。

使用同一稳定用户身份去重；当前参考与未来预约分开。有效堂食、近期位置或近期取餐的组合按 contracts 统一计算，不把多份菜算多人，不把外带或已退款算堂食。位置 10 分钟、取餐 30 分钟仅为配置示例。UNKNOWN / 过期 / 校准不足与零值分开，展示依据、更新和演示标记。位置由客户端报告，不能作为真实性或权限凭证。

提供可调整、可测试的食堂范围参数和误差处理示例；错误大或边缘不确定返回 UNKNOWN。不要让学生端自行选择算法和阈值。拥挤指标不限制购买或强制外带；单档口数据不外推全食堂实测人数。

## 管理端最小范围

档口与营业时间、订单及异常查询、食堂范围与提醒条件即可。管理页共用 API，不直接绕过订单校验改数据。不做复杂权限管理界面、财务、花哨报表或新增第四套系统。根配置变化集中处理。

## 单 APK 公共职责

你负责 apps/mobile 的单一入口和账号登录、服务端授权后的角色入口、src/app/ 页面切换、src/shared/ 请求与定位封装、公共依赖和锁文件、安卓工程及 APK 构建。三角色模块合入同一应用，不能各打各的包再临时拼接。管理模块位于 apps/mobile/src/modules/admin。只协调学生/档口模块适配，不直接改写其业务代码。
